Genesis · Local-AI Linux distribution

Can we build a Linux that builds things for you, entirely on local models?

A four-angle investigation, from Linux engineering, model research, UX, and implementation, into an operating system where several local LLMs are a first-class service and an agent can build apps, browse, install software and reconfigure the machine.

Prepared 2026-09-10For Matija GorsekResearch via 8 specialist agents, ~450 source fetches

Verdict

Yes. It is feasible, and no core piece needs to be invented. Every layer has a mature open-source component to reuse: an image-based Fedora base with rollback, llama.cpp with a model-swapping router, an Apache-licensed Rust agent engine that speaks MCP, sandboxing already proven by Claude Code and Codex, and a 2026 crop of Apache 2.0 models that run on consumer GPUs.

The real constraints are hardware and honesty. Reliable agentic app-building starts at about 24 GB of VRAM with a 27B-class coder. On 16 GB it works for scoped tasks with retries. On CPU-only laptops it is a chat assistant, not a builder. The distro must detect hardware and set expectations at first boot.

Effort: a working prototype in a VM in 8 to 10 weeks. An installable alpha in about 6 months. A beta with the app-builder and safe browsing in roughly 12 months. Two to three people.

Base

Fedora bootc, KDE Plasma

Image-based, read-only /usr, bootc rollback. Fork the Aurora image from Universal Blue. NixOS is the runner-up.

Inference

llama.cpp + llama-swap

One OpenAI-compatible endpoint on localhost. Small model always hot, large models swap on demand. Vulkan everywhere, CUDA and ROCm via containers.

Agent

Goose embedded in Rust daemons

Apache 2.0, MCP-native, under the Linux Foundation. Genesis adds the permission broker, snapshots and undo, and local-model hardening.

Models

Qwen3.5 / 3.6 / 3.8 family first

Apache 2.0 at every size, natively multimodal, best open scores per parameter. Gemma 4 and gpt-oss as alternates.

Models: what to ship for "several LLMs"

The design assigns one model per role, and a router picks by task. The Qwen3.5 through 3.8 line dominates the 2026 open-weight field at consumer sizes, is Apache 2.0 at every size, and is natively multimodal, which removes the need for a separate vision model in most packs.

Evidence on capability

Community reports converge: Qwen3.6-27B pointed at OpenCode or a similar agent harness gives "genuinely useful agentic runs" comparable to small hosted models on multi-file refactors. Local models still take shortcuts, loop after a failed tool call, or lose the architectural thread on large cross-repo work. Local sits at roughly 70% SWE-bench versus 80% for frontier cloud. One practical warning: Q4 quantization degrades tool-call formatting on 20 to 40B models, so use Q5 or Q6 for the agent model when memory allows.

Runtime choice

llama.cpp's llama-server behind llama-swap is the system service. It gives per-model process control, groups that keep small models resident while large ones swap, TTL unloading, an OpenAI-compatible API, and grammar-constrained JSON for tool calls. Ollama is easier to start with but its model store is proprietary-shaped, its eviction policy is a global setting, and Fedora's packaging of it stalled in July 2026. Keep an Ollama-compatible shim on port 11434 for app compatibility. vLLM only for multi-GPU workstations. Speculative decoding (EAGLE-3 or MTP in llama.cpp) roughly doubles throughput on dense 27B coders and should be enabled per model, but it slows down the 35B-A3B MoE models and must stay off there.

Fedora treats weights as content and allows them under approved licenses. Debian has no binding weights policy after its 2025 proposal was withdrawn. The OSI's Open Source AI Definition requires training-data documentation that almost no model meets, so describe Genesis as "open weight", not "open source AI".

Recommendation: fork the Aurora image (KDE on Fedora bootc). Immutability is the safety net for an autonomous agent. Steal NixOS's best idea anyway: give the agent one declarative layer under /etc/genesis/ and a genesis apply command that validates, snapshots, and applies, instead of letting it hand-edit arbitrary files. Note the tradeoff: on bootc, "install software" means Flatpak, Homebrew, distrobox containers, or a PR to the image, never dnf install on the host. That forces a clean permission tier model, which is a feature.

Why KDE Plasma over GNOME

Plasma has the richest automation surface: KWin scripting, KRunner D-Bus runners, global shortcuts, a working MCP server prior art (kwin-mcp). GNOME has the best accessibility tree but its community policies now reject AI-generated extensions and ban LLM contributions in several core apps, which makes it a hostile venue for an AI-native distro. Use xdg-desktop-portals for screenshots and input so the same code works on GNOME later.

GPU story, least painful path

  • Vulkan everywhere on the host. One llama.cpp build covers NVIDIA, AMD, Intel and older cards with acceptable performance.
  • Two image flavours like Bazzite: genesis (Mesa) and genesis-nvidia (nvidia-open kernel modules, signed for Secure Boot). Skip the legacy proprietary driver at launch; Pascal-era cards get Vulkan or CPU.
  • CUDA, ROCm and SYCL as pullable containers via ramalama, selected by the hardware profile. Never bake multi-gigabyte vendor stacks into the base image.

Socket-activated on desktop login, not at boot. A tiny 4B model stays warm for latency-sensitive features. Large models load on demand with a 10-minute TTL, shorter on battery. A small D-Bus service (org.genesis.AI1) owns the model catalog, hardware profile and download progress so desktop widgets have something to talk to.

Model storage and distribution

Do not bake models into the ISO. Ship one 1 to 2 GB bootstrap model for the installer's assistant, then download the chosen pack at first boot. Transport: OCI artifacts using the Docker model-spec media types that CNCF ModelPack is converging on, hosted on GHCR, content-addressed and resumable. ramalama already pulls from OCI, HuggingFace and Ollama registries. Layout lives under /var/lib/genesis/models/ because /usr/share is read-only on bootc.

Two lessons from 2026 incidents. A bubblewrap escape in April showed that denylists do not work, only allow-listed mounts. And the Comet browser's prompt-injection disclosures showed that once an agent has read untrusted web content, its write permissions must drop to "ask" regardless of mode. The agent runs as its own Unix user, never as the human. Secrets go through the keyring broker at execution time so the model never sees raw tokens.

The "build an app" loop

  1. Hot model classifies intent as "build app". Coder model writes a short spec and picks a template from a fixed list via grammar-constrained output.
  2. Templates ship with tests, lint and a justfile: Vite web app, HTMX plus Python, Rust CLI, Python script, GTK4 or Qt desktop app, each with a Flatpak manifest.
  3. Scaffold into ~/Projects/name and open a transaction.
  4. Edit, run just check and just test, parse failures, retry up to N times, then ask. Use search-and-replace edit blocks, not whole-file rewrites.
  5. Preview in an embedded WebKitGTK view or launch the binary in a nested sandbox. Playwright runs smoke tests. The vision model answers "does it look right?".
  6. Install via flatpak-builder in podman. A desktop entry appears. Undo remains available for 7 days.

Reliability tactics that matter with local models: JSON schema or GBNF grammars for every structured step, at most 8 tools exposed per turn with the hot model picking the tool group first, temperature near zero for tool turns, a plan-then-execute split between the chat and coder models, and a CodeAct-style Python micro-executor for the 4B model.

Multi-model routing

The research is clearer than the hype. The 2026 LLMRouterBench study found that sophisticated routers, including commercial ones, rarely beat a simple baseline, and that most of the gap to an oracle comes from the models themselves, not the router. So keep it boring.

route(request):
  if request.model is pinned:            return that model
  caps  = needs(request)                 # vision? tools? json schema? context length
  tier  = calling surface                # shell completion / chat / agent / vision / batch
  if tier == shell:                      return coder-1.5B (always hot, n-gram spec decoding)
  if caps.vision:                        return vision model (deterministic)
  intent = hot_4B.classify(last_turn, grammar=enum[chat,code,system,research,trivial])
  if intent == trivial and ctx < 2k:     return hot_4B
  order  = policy_table[intent]          # e.g. code → [coder-27B, chat-35B-A3B, hot]
  for m in order:
      if m fits caps and (m resident or vram_plan.can_load(m, keep=hot tier)): return m
  if cloud enabled for this intent and no local-only content in context: return cloud
  return best resident with a visible "degraded" note
  • Route by surface first, content second. Where the request came from is a free, perfect signal.
  • Agent sessions pin their model for the whole task. Sub-steps like summarizing tool output go to the hot model.
  • Escalation uses the small model's own uncertainty (average log-probability), not a second classifier. Cap the escalation rate to protect VRAM.
  • Hysteresis: after a swap, keep the new model at least two minutes. Queue, do not thrash.
  • Rebuild the policy table offline whenever the installed model set changes: embed a task corpus, cluster, score each model per cluster on a few hundred samples. This is the Avengers method and needs no trained router.
  • Cloud is off by default. If any chunk from a local-only directory is in context, cloud is blocked for that request.

UX and product

What the market is teaching, harshly

Windows Copilot and Recall

Forced, branded AI in every core app produced a backlash ("Microslop"), and Microsoft spent 2026 removing Copilot from Notepad, Photos and Snipping Tool. Recall's always-on capture was blocked outright by Signal, Brave and AdGuard. Lesson: opt-in, unbranded, local-first.

Apple's Siri revamp

Slipped repeatedly, settled a class action over unshipped features, and the WWDC 2026 demo drew "not nearly half way there" from Hacker News. Lesson: never demo what does not reliably work. Set expectations by hardware tier.

Comet, Dia, Brave Leo

Browser agents were hijacked by hidden text on Reddit posts and in screenshots. Brave's answer is the pattern to copy: isolated cookie-less profile, visible actions, confirmations, and a second model checking intent.

Raycast, Alter, Newelle

Raycast users resent paying for AI twice. Alter wins on context-aware actions and weekly shipping. Newelle, the GNOME assistant, is criticized as not "install and use": it needs API keys. Genesis's first-boot pack download must make it work with zero setup.

Design principles

  • The model is invisible by default, never hidden. Automatic routing, with a small badge showing which model answered and a one-click override to Fast, Smart, Code or Vision. Full manual pickers belong in settings.
  • Everything local is the brand. A persistent indicator that reads "on this machine" and turns amber only when a cloud key is in use. Never a splash screen promise.
  • Show work, not magic. Long agent tasks render as a plan with live steps, file diffs, terminal output and browser actions, all interruptible and steerable mid-run.
  • Every change has an undo. The session summary lists what changed on the system and offers one button to revert it.
  • Latency is honest. The hot model answers within a second and the stronger model refines under it. Never a blank spinner.
  • Tool, not persona. No mascot, no name that speaks in first person. "Genesis" names the system. Avoid the Clippy trap.

Roadmap and risks

Weeks 1 to 10

Phase 0 · Prototype in a VM

Bluefin or Aurora VM. llama-swap with a hot 4B and a 27B coder. Gateway v0 routing by surface and intent. Goose driven over ACP. Plasma hotkey launcher. Shell and filesystem MCP in bubblewrap. Audit log.

Exit: ask anything, run a command, edit a repo from the hotkey, fully local, with prompts for writes.

Months 3 to 7

Phase 1 · Alpha image

bootc image built in GitHub Actions with two flavours. ramalama quadlets. Permission broker with modes and policy files. Transactions with btrfs snapshots and an undo UI. sqlite-vec indexer. SearXNG. First-run wizard with pack download. Zed via ACP.

Exit: installable ISO; undo works for user and system-scope changes; three model tiers swap without OOM on 16 and 24 GB GPUs.

Months 8 to 13

Phase 2 · Beta

App builder with templates, preview and Flatpak packaging. OpenHands builder container. Playwright browsing with sanitized fetch and injection defenses. Desktop control via AT-SPI and portals. Package and sysconfig MCP. Cloud BYOK.

Exit: ten scripted "build me X" tasks pass with the local 27B; browsing survives an injection test suite.

Months 14 to 20

Phase 3 · Stable

microVM tier for untrusted code. Sealed images with UKI. Voice in and out. ROCm, Intel and NPU backends. Security review against the OWASP Agentic Top 10. Thirty-day dogfood without data loss.

Top risks

  1. Local model reliability on multi-step tool use. Mitigate with grammars, small tool sets, verification loops, and cloud BYOK as a pressure valve.
  2. VRAM contention between hot, coder and vision models on 16 GB cards. The gateway must serialize loads; llama-server's router has a known race under concurrency.
  3. Wayland desktop control stays portal-gated, and GNOME's next accessibility stack may change AT-SPI. Abstract it behind one trait.
  4. Upstream churn: Goose's API, OpenHands's V1 SDK rewrite, bootc's move to composefs and sealed images. Pin versions, vendor thin adapters.
  5. Security exposure. An OS-level agent is a high-value target. Red-team injection and privilege escalation continuously.
  6. Fedora has no official bootc desktop image yet, so you depend on Universal Blue's bases. Bluefin reports this is resolving in 2026.

What to do this week

  1. Spin up a Bluefin or Aurora VM under UTM or OrbStack on the Mac. The dev loop for RPM-level image changes runs there; GPU tests need one Linux box with a 24 GB card.
  2. Install llama-swap and llama-server, load Qwen3.5-4B and Qwen3.8-27B, and confirm the swap behaviour on your target hardware.
  3. Point Goose at that endpoint and try three real tasks: a shell command, a repo edit, a small web app. That single afternoon tells you more than any benchmark about whether the core feels good enough.
  4. Only then start the image repo, using the layout in the Linux report: Containerfile, system_files/, packs/, src/ for the Rust daemons, and GitHub workflows for image, ISO and VM tests.

Unverified items and gaps

The research agents hit search limits and flagged the following. Check before committing.

  • llama-swap support for systemd socket activation. Fallback is systemd-socket-proxyd.
  • Exact CUDA 13.x EULA redistribution list before shipping CUDA userspace in the image. Container delivery avoids the question.
  • Goose's headless server API and approval modes were verified only at README level. OpenHands's bubblewrap backend came from a secondary source.
  • Several benchmark leaderboards (SWE-bench, Terminal-Bench, LiveCodeBench, BigCodeBench) are JavaScript-rendered and were read via mirrors or vendor model cards. The Aider leaderboard appears unmaintained since October 2025.
  • Claims of a "Llama 5" in April 2026 come from one low-quality source and contradict Meta's record. Treat as false. Meta's 2026 open model is Muse Glimmer 30B.
  • Mistral Small 4 architecture conflicts across sources (119B-A6B MoE vs 24B dense). Mistral Medium 3.5's "modified MIT" license is from a third-party tracker only.
  • Many community Qwen3-Reranker GGUFs lack the classification head and return meaningless scores. Use a correctly converted file or bge-reranker-v2-m3.
  • KDE's official plans for a local assistant, and COSMIC's accessibility maturity, were not confirmed from first-party sources.
  • The UX sub-research on coding-agent interfaces and model-manager apps was cut short by a usage limit. The v1 surfaces above draw on the spreadsheet counts, the OS-assistant landscape, and the architecture team's review of current coding-agent tools.
